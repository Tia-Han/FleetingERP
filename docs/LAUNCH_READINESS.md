## 本轮范围

新增数据库可用性检查、商品与 SKU 乐观并发校验，修复 SKU 规格/容量不保存和缺省条码被清空。接口 GET 返回 revision，编辑必须携带读取时的 revision；过期或缺少版本返回 409，不写入。网页和小程序商品编辑均已适配。内容指纹实现无需数据库迁移；它保护商品和 SKU 编辑，不代表其他主数据具备同样保护。

本轮不新增分装、退款、批次、多场所授权，也不更换数据库。订单收款目前是人工登记支付方式与金额，不是微信支付扣款、自动核款或退款系统。

## 网页可以开始使用吗

结论：本轮部署且下列现场验收通过后，可以启动一仓两店、约三名员工的小范围试运行；尚不能承诺所有功能零缺陷，不能仅凭自动测试直接宣布全面正式上线。

开始录入正式业务前，必须确定：

1. 每人独立账号，绑定正确场所，管理员密码独立保管。测试数据保留归档；需要清空测试账时另做明确的数据初始化方案，不直接删库。
2. 记录初始实物库存，并与系统各场所、各 SKU 对上。不要把测试库存作为正式期初库存。
3. 备份复制到另一设备/存储，验证副本完整性并实际演练恢复。当前同机备份不能覆盖 ECS 整机丢失。
4. 用标记的测试商品执行：入库 10 → 调拨 3 到门店 → 门店售出 1 → 仓库余 7、门店余 2；入出库历史、销售记录、金额和流水一致。
5. 盘点差异记录原因，核对流水；两次点击不能重复扣库；超库存销售被拒绝；门店 A 无权读写门店 B；仓管不能销售。
6. 两个管理员打开同一商品/SKU，先后保存，第二次应显示冲突且不覆盖；重新打开后可正常修改。
7. 重新登录、强制刷新、观察健康检查和错误日志，PM2 保存并检查自启动。

试运行期间每日核对库存、销售额和备份。积分流水、不可变单据快照、版本化迁移、金额存储统一与业务日期规则仍是后续独立改造，不能标记为已完成。若立即依赖积分兑换、严格历史凭证或财务核算，应先完成相应改造再开展该业务。不要用手工 SQL 修改销售金额、支付和积分来“冲正”。

## 小程序最快落地路径

已有原生小程序代码和共享后端，不需要另建数据库或重写系统。现有页面包含登录绑定、扫码、销售、库存、入出库、盘点、客户、商品和品牌；没有完整的调拨开单页面及网页版的用户/备份管理。管理员配置和调拨可先在网页完成。分装继续关闭。

### 平台准备（需账号管理员操作）

- 在微信公众平台确认小程序账号、主体、实际 AppID、开发者权限、服务类目、备案及隐私保护要求，以登录后的平台检查项为准。仓库现有 AppID 不能当作账号归属已验证。
- 下载微信开发者工具，导入仓库根目录（包含 project.config.json）；它将 miniprogram/ 作为源码目录。不要同时维护两份不同 AppID 的导入项目。
- 配置 request 合法域名为实际 HTTPS API 主机。API 地址在 miniprogram/app.js；域名配置只填主机，不填 /api/v1 路径。保持域名和证书校验开启，不能用模拟器跳过校验替代真机验证。
- 后端需要 WX_APPID、WX_APPSECRET，必须与小程序一致。AppSecret 只存服务器受保护环境文件，不能进 Git、截图或聊天。配置改变后受控重启后端。
- 首次通过微信登录后绑定管理员在网页创建的独立员工账号；不共用管理员账号。网页与小程序共用同一账号时，后登录会使先前会话失效，这是当前设计。

### 体验版先行

1. 开发者工具编译，处理所有实际编译错误；源码测试不能代替 WXML 渲染和微信 API 验证。
2. 配好后端与域名，在真机分别用店员、仓管、管理员测试。扫码应覆盖已有条码与未知条码；权限被拒绝时不得修改库存。
3. 验证首次绑定、后续微信登录、退出、会话失效、弱网重试、销售折扣、库存不足、入出库部分失败、历史详情和商品修改。
4. 上传开发版本，在公众平台配置体验版及指定体验人员。先由三名员工按同一套测试用例验收；体验版不能当作正式发布已经完成。
5. 根据平台要求补齐审核资料、隐私说明及审查所需测试路径，再提交审核；通过后由管理员发布。审核和备案时长不由代码开发决定，不承诺具体天数。
